YO！今天的副本是「双线程流水线」。
带上 357ms 和 130ms 这两把钥匙，出发！
QUEST
"接收 1KB 约 90ms，收 4KB 就要 357ms；可擦除+写 4KB 也要 130ms。 双线程到底是怎么把这两个时间凑到一起的？具体每一步在干什么？"

LEVEL 1 先算账：单线程为什么必死 ▶

■ 两个数字摆上台面

  • 串口 115200：约 11.5KB/s → 收 4KB 要 357ms
  • W25Q64 擦+写 4KB（一个扇区）：擦 ~45ms + 页写 ~84ms ≈ 130ms

看上去 130 < 357，"写比收快"，好像没事？错——关键在于这两件事能不能同时干。

单线程：357ms(收) + 130ms(写) = 487ms / 4KB 而数据每 357ms 就到一批 —— 每块亏 130ms，只进不出

■ 单线程的死亡螺旋

收完 4KB → 停下来擦写 130ms → 这 130ms 里串口又到了约 1.4KB → 先攒流缓冲。 下一块再亏 130ms……流缓冲 4096B 迟早溢出，丢字节 → 固件损坏。 就算改用 Ymodem 停等（发送方等 ACK 自动不推数据）不死机，每块也要白白多花 130ms——串口在写 Flash 时干等着。

■ 中间结论

收包和落盘是两台节奏不同的机器，必须让它们并行：OTA 线程专职收，下载线程专职写。

LEVEL 2 双线程分工：两张工位图 ▶

对应 OtaApp.c：OTA 线程 = OtaApp_Task，下载线程 = OtaApp_DownloadTask。

■ 为什么 OTA 线程优先级高、下载线程低？

收包有实时性（DMA 波次 + IDLE 中断要求及时搬走），而写 Flash 是"慢工活"，晚一点无所谓。 让快的等慢的可以，让慢的堵快的不行。

▸ 七个工位逐个拆开看

工位① 串口 + DMA（硬件自动，CPU 零参与）

  • 串口每收到 1 字节，DMA 自动搬进 s_rx_chunk[1024]——不进中断、不打扰任何线程
  • 为什么是 1024？正好一个 STX 数据帧的长度。停等协议下回完 ACK 对端才发下一帧，所以一波 DMA 基本装下完整一帧（帧总长 1029 = 头5+数据1024）
  • 这一步没有任何软件参与——你写代码时可以当它"不存在"

工位② IDLE 空闲中断（第一程软件搬运）

  • 触发条件：总线静默超过 1 字节时间（115200 下 87µs）。注意它只认"安静"，不认"帧尾"——只是停等协议恰好让一帧发完后线就安静了，所以效果上等于帧尾中断
  • 进 OtaApp_OnRxEvent（ISR 上下文）只做两件事：把刚到的 len 字节从 s_rx_chunk 拷进流缓冲 → 重挂 DMA 等下一波
  • ISR 铁律：只拷贝不处理、不阻塞、不调任何带超时的 API。喂帧的事交给 OTA 线程

工位③ 流缓冲 4096B（节奏缓冲带）

  • 作用：把中断的波次节奏（一波 1029B，随时可能到）和任务的消费节奏（OTA 线程每轮最多取 128B）解耦
  • ISR 侧 xStreamBufferSendFromISR 写入，OTA 线程 xStreamBufferReceive 读出——一写一读天然线程安全，无需自己加锁
  • 停等协议下压力极小（发送方等 ACK 不推数据），4096 是余量设计；满时 ISR 丢弃新数据，坏帧会被 CRC 抓住重传

工位④ OTA 线程凑帧（Ymodem 子状态机）

  • xStreamBufferReceive 带 20ms 超时——超时返回 0 字节，正好轮去做空闲检查（这个超时既是取数粒度也是看门）
  • 取到的每个字节喂 Ota_YmFeed(b)，六状态推进：HEAD→SEQ→SEQC→DATA（边收边算CRC）→CRC_HI→CRC_LO
  • CRC 低字节一到 → Ota_YmFrameDone 整帧裁决：过 → 落缓冲；不过 → NAK 重传，4KB 缓冲毫发无损（帧数据一直只待在独立的 s_ym_frame 里）

工位⑤ 4KB 缓冲 ×2（所有权交接核心）

  • Ota_YmToBuf：当前缓冲是空的（s_cur_len==0）→ 先 Ota_BufTake 拿"空闲"信号量（唯一可能阻塞的点，稳态只等 41ms）→ memcpy 1024B 进去
  • 攒满 4096 → Ota_BufCommit：往队列塞 16 字节消息 {指针, len, id, session 轮次号} → 切另一块继续收
  • session 是防串轮的：每进一次下载 s_session++。下载线程收到消息发现轮次号变了 → 写指针归零从头写。没有它，第二轮会接着上一轮的半截位置往下写，把 A 区写花

工位⑥ 满块队列（交接窗口）

  • 深度 = 2 = 缓冲块数。每块交出去之前一定先 take 过信号量 → 队列里最多同时躺着 2 块 → put 永远不阻塞，这是设计出来的数学保证
  • 下载线程 osMessageQueueGet(..., portMAX_DELAY)：取不到就睡，零 CPU 占用，来一块醒一次

工位⑦ 下载线程擦写 W25Q64

  • 取块 → 按写指针算覆盖哪些 4KB 扇区 → 跨扇区边界先擦（擦过的扇区记下来不重擦）→ 按 256B/页连续写
  • 写完（无论成败）→ release 信号量把缓冲还回去。失败不还 = OTA 线程永远卡死在 BufTake，整条流水线停摆——所以 release 必须无条件执行
  • 写失败 → 置 s_wr_error → OTA 线程在喂帧间隙发现 → 中止本轮、不发正响应 → 服务器可以重传整包

■ 为什么队列传指针不传 4KB 数据？

队列拷贝按消息大小来。传 4KB = 每块多 4KB 内存搬运还多 4KB 队列存储； 传指针 = 16 字节搞定，缓冲本体由信号量保护，一块内存只有一个人在写。 这就是"拷贝不共享"策略：共享的只是"这块现在归你"这个所有权凭证。

/* 队列深度 = 缓冲块数 = 2 —— 数学上不可能满 */ s_frame_q = osMessageQueueNew(OTA_BUF_COUNT, sizeof(OtaFrame_t), ...); /* 交出前一定先 take 过信号量 → 队列里每块都对应一次take */ /* 所以 put 永远不会因队满而阻塞，这是设计出来的不变量 */

■ 中间结论

信号量管所有权，队列管交接，流缓冲管中断与任务的节奏差——三件套各管一段，谁也不越权。

LEVEL 4 时间线：130ms 只露出 41ms ▶

Ymodem 是停等协议：MCU 每收完一帧 CRC 校验通过、数据落进 4KB 缓冲后才回 ACK，发送方收到 ACK 才发下一帧。 一帧 1024B 传输约 89ms，4 帧凑一块 4KB。

单缓冲：356 + 130 = 486ms/块   →   双缓冲：356 + 41 ≈ 397ms/块 双缓冲把"完整等 130ms"压缩成"只等差值 41ms"；推流版则能 100% 藏掉(357>130)

■ 为什么停等版不怕 BufTake 阻塞堆数据？

推流版里 OTA 线程阻塞 130ms，串口还在推 → 靠流缓冲硬扛。 停等版里 ACK 就是阀门：OTA 线程不回 ACK，发送方就停在那里——数据根本不会来。 之前的"背压三级闸"在停等协议下收敛成一句话：ACK 时机即流控。

■ 验证卡：两条路复核 41ms

路线A(画图)：帧5在 t=356~445 传输；块A在 t=356 开写、t=486 写完 → 帧5收完时剩 486-445 = 41ms。 路线B(公式)：露头时间 = 写块时间 − 一帧传输时间 = 130 − 89 = 41ms。两路一致 ✓

稳态周期 = 4×89 + 41 ≈ 397ms/块；波特率降到 76800 以下(一帧≥135ms)时，帧传输能盖住整个 130ms 写块，41ms 归零

■ 中间结论

停等版的 41ms 等待，本质是"帧传输(89ms)追不上写块(130ms)"的差值：130−89=41。波特率越高、一帧传得越快、差值越大——921600 下会涨到 119ms，那时瓶颈就真正变成 Flash；而流水线的妙处是：无论差值多大，缓冲信号量自动让 OTA 线程等在 BufTake，不用改一行代码。

■ 中间结论

传输层(CRC+停等)管"坏帧当场重传"，文件层(MD5)管"整包一致性"——两层防线，坏帧不过夜，坏包不转正。

■ 会话超时也换班了

老版 3 秒空闲 = "推流结束"；新版 3 秒空闲 = 异常：握手段没等到帧0 → 重发 'C'（最多10次）； 收到帧0后空闲 → 对端死了，发 CAN 挂断中止。正常停等节奏是毫秒级，3 秒静默绝不正常。

⚠ BOSS战警告
  1. 坑1：CRC 还没算完就发 ACK。正解：CRC过 → 落RAM缓冲 → 才ACK。顺序错一步，Flash 里全是垃圾还以为传好了。
  2. 坑2：把重复序号当新帧再填一遍。正解：seq==expected-1 是"上个ACK丢了"的对端重传，重 ACK 即可，填了数据就错位。
  3. 坑3：收到第一个 EOT 就 FinishDownload。正解：标准双EOT握手——第一次回NAK，第二次回ACK+'C'要结束帧。回错对方一直重发EOT，两边卡死。
  4. 坑4：EaSize 直接写 s_total。正解：Ymodem 0x1A 填充会混进字节数，Boot 的 cipher_len==16+body_len+16 互验必挂。用帧0里的文件大小。
  5. 坑5：下载线程写失败不还信号量。正解：无论成败都必须 release——不还的话 OTA 线程永远卡死在 Ota_BufTake，整条流水线停摆。
