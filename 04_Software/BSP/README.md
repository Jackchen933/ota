# ST7789 驱动（BSP）

## 分层

```
bsp_st7789.c ──────── 驱动本体，平台无关，不含任何 HAL 头文件
     │                 只通过下面三个接口与外界打交道
     ├── basic_op_driver_interface_t   SPI + RESET/CS/DC 三个 GPIO
     ├── st7789_timebase_interface_t   HAL_GetTick / HAL_Delay
     └── st7789_yield_interface_t      让出 CPU（裸机空实现）

bsp_st7789_port.c ─── 板级实现，把 HAL 接到上面三个接口上
```

换 MCU 时**只重写 `bsp_st7789_port.c`**，驱动本体一行都不用动。

## 接线

| STM32F411 | 屏幕 | 说明 |
|---|---|---|
| PB13 | SCL / SCLK | SPI2_SCK，AF5（**不是默认的 PB10**，PB10 已释放） |
| PB15 | SDA / MOSI | SPI2_MOSI，AF5 |
| PA8 | CS | GPIO 输出 |
| PA11 | RES / RST | GPIO 输出 |
| PB14 | DC | GPIO 输出 |
| 3V3 / GND | VCC / GND | |
| — | BLK | 背光，本项目未接管 |

> **SCK 为什么在 PB13 而不是 PB10**：STM32F411 的 SPI2_SCK 有两个可选引脚——
> PB10(AF5) 和 PB13(AF5)。本板走线用的是 PB13，所以 CubeMX 里把 SPI2_SCK
> 选到了 PB13，PB10 释放。改错这个引脚的表现是**屏幕完全没反应**
> （时钟根本没送到屏上），而不是花屏。

SPI2 配置：Master / 8bit / **CPOL=High, CPHA=2Edge (Mode 3)** / 25 MHz / TX-only
DMA：DMA1_Stream4 CH0 → SPI2_TX

> SPI2 的 `Direction` 在 [spi.c](../Core/Src/spi.c) 里是 `SPI_DIRECTION_2LINES`，
> 但 MISO(PB14) 被拿去当 DC 用了。发数据不需要 MISO，HAL 也会自己清 OVR 标志，
> 所以能正常工作。想干净一点可以在 CubeMX 里改成 `TX Only Simplex`。

## 已实现的 API

| 函数指针 | 说明 |
|---|---|
| `pf_st7789_init` | 复位时序 + 完整初始化序列 |
| `pf_set_addr_window` | 设置刷屏范围（含 `X_SHIFT` / `Y_SHIFT` 偏移） |
| `pf_fill_color` | 全屏刷指定颜色 |
| `pf_fill` | 矩形区域填充 |
| `pf_draw_pixel` | 单像素 |

其余 15 个函数指针（画线/矩形/圆/三角/字符/图片/tear effect 等）保持 `NULL`。
调用前用 `ST7789_ASSERT_PTR(p)` 断言，否则会 HardFault。

## 用法

```c
bsp_st7789_driver_t *lcd = bsp_st7789_port_init();
if (lcd == NULL) { Error_Handler(); }

lcd->pf_fill_color(lcd, ST7789_RED);
lcd->pf_fill(lcd, 70, 130, 169, 189, ST7789_WHITE);
lcd->pf_draw_pixel(lcd, 0, 0, ST7789_BLACK);
```

`bsp_st7789_port_init()` 内部会调用 `pf_st7789_init`。调用前必须先执行
`MX_GPIO_Init()` / `MX_DMA_Init()` / `MX_SPI2_Init()`。

## 关键设计说明

### 没有整屏 framebuffer

`240 × 320 × 2 = 153600` 字节 > STM32F411CE 的 128 KB RAM，放不下。
所以用**条带缓冲**（`disp_buf`）：每次只缓冲 `ST7789_HOR_LEN` 行，
靠循环多次 DMA 拼出整屏。

- 占用 RAM = `ST7789_WIDTH * ST7789_HOR_LEN * 2`
- 当前 `ST7789_HOR_LEN = 8`，即 `240 × 8 × 2 = 3840` 字节
- `ST7789_HOR_LEN` 的取值受 DMA 单次传输上限约束（NDTR 是 16 位，
  最大 65535 字节）：`240 × N × 2 ≤ 65535` → `N ≤ 136`。
  取 8 是 RAM 和刷屏速度的折中点
- RAM 吃紧就调小（画面由多次 DMA 拼出，条带越少刷得越慢），
  要刷得更快就调大，上限 136

### RGB565 字节序

ST7789 要求**高字节先发**，Cortex-M 是小端：`0xF800`（红）在内存里是 `00 F8`，
按字节 DMA 出去会变成 `0x00F8`，颜色全错。驱动里用 `ST7789_COLOR16()`
统一做了交换，见 `ST7789_SWAP_COLOR_BYTES`。

### DMA 是异步的

`HAL_SPI_Transmit_DMA()` 立刻返回，所以 `port_spi_transmit_dma()`
阻塞等到完成回调置位才返回，上层才能认为"数据发完了"。
等待期间有超时兜底，超时会 `HAL_SPI_Abort()` 把 SPI 状态复位。

## 刷出来不对时怎么调

按现象对照改 `bsp_st7789.h` / `bsp_st7789.c` 顶部的宏：

| 现象 | 改哪里 |
|---|---|
| 颜色整体反相（黑底变白底） | `ST7789_CMD_INVON_ENABLE` 改成 0 |
| 红蓝互换 | `ST7789_MADCTL_DATA` 改成 `0x08` |
| 图像整体偏移、边缘有条纹 | `ST7789_X_SHIFT` / `ST7789_Y_SHIFT` |
| 颜色乱七八糟不像色块 | `ST7789_SWAP_COLOR_BYTES` 改成 0 |
| 全黑，什么都没有 | 先量背光；再查 RESET/CS/DC 接线；再查 SPI2 时钟 |
| 花屏 / 随机噪点 | SPI 速率太高，CubeMX 里把 BaudRatePrescaler 调大一档 |

`X_SHIFT` / `Y_SHIFT` 怎么定：屏幕四角各画一个点，
如果点不在角上，偏移量就错了。240x320 的屏一般为 0；
240x280 的屏纵向通常是 20。

# CST816S 触摸驱动（BSP）

## 分层

`bsp_cst816s` **没有**像 ST7789 那样拆成"驱动本体 + 板级移植"两层，
只有一个 [bsp_cst816s.c](Src/bsp_cst816s.c)：

| | ST7789 | CST816S |
|---|---|---|
| 代码行（不含注释） | 382 + 移植层 123 | 433 |
| 依赖 | SPI + 3 根 GPIO + 时基 + 让出 CPU | 两个普通 GPIO |
| 拆分的收益 | 换 MCU 只重写 port 层 | 无 |

判断依据是**这层抽象到底省掉了什么**，不是行数。ST7789 拆出来，
是因为驱动本体（初始化序列、绘图原语、坐标变换）和 STM32 完全无关，
换 MCU 时那 382 行能原封不动搬走；CST816S 拆出来只会多两个文件，
换 MCU 时照样得整篇重写 —— **它没有"平台无关的内核"可抽**，
每一行都是"在 PB6/PB7 上打时序"这件事本身。

> 早先这里写的是"ST7789 上千行 / CST816S 约 400 行"。那组数字是把
> ST7789 的**总行数**（含注释）和 CST816S 的**纯代码行数**拿来比，
> 量纲都不一样。按同一个口径，CST816S 其实比 ST7789 的内核还长一点
> —— 所以"行数少"从来就不是不拆的理由，理由是没有可抽的内核。

## 接线

| STM32F411 | CST816S | 说明 |
|---|---|---|
| PB6 | SCL | **当普通开漏 GPIO 用**，不接 I2C1 外设 |
| PB7 | SDA | 同上 |
| PB0 | RST | GPIO 输出，低电平复位 |
| — | INT | **本项目未接管**，见下方说明 |
| 3V3 / GND | VCC / GND | |

> **PB6/PB7 在 CubeMX 里仍然配成 I2C1 的 AF4 复用脚**，这是有意的：
> `MX_I2C1_Init()` 在 `main.c` 里照常调用，被驱动接管的只是引脚本身。
> 这样重新生成 CubeMX 代码不会把这段配置冲掉，也不会有人以为
> "I2C1 没用上，那配置删了吧"。驱动在 `bsp_cst816s_init()` 里
> `HAL_I2C_DeInit()` 一次，把两个脚取过来自己翻转电平，之后
> **再也不碰 I2C1 外设**。为什么这么做见下面《为什么改成软件模拟》。

**这条总线上唯一驱动高电平的是上拉电阻。** MCU 侧永远是开漏
（`GPIO_MODE_OUTPUT_OD` + `GPIO_PULLUP`，写 1 = 放开），从机也是开漏，
所以"1"是上拉拉出来的、"0"是被某一方拉下去的。这带来一个重要的推论：

> **上拉缺失时不是"读不准"，而是彻底读不到。** 内部上拉约 40 kΩ，
> 对一个 3.3V 系统来说太弱了——线容性负载稍微大一点，上升沿就慢到
> 在半个位周期（约 11 µs）内根本爬不到高电平。但慢的上升沿同时也
> 意味着**没有毛刺、没有 BERR**，任何"电气干扰"的特征都不会出现，
> 只有连续的超时。CST816S 的模块/排针小板一般自带上拉；
> 如果是裸芯片自己搭，SDA/SCL 上各加一个 4.7 kΩ 到 3V3。

## API

| 函数 | 说明 |
|---|---|
| `bsp_cst816s_init()` | 接管引脚 + 硬件复位 + 校验 ChipID + 关自动休眠 |
| `bsp_cst816s_read(out)` | 读一次触摸状态和坐标（含 6 个原始字节） |
| `bsp_cst816s_chip_id()` | 取初始化时读到的 ChipID（`init` 之后才有值） |
| `bsp_cst816s_autosleep_rc()` | 取 init 时"关自动休眠"那次写的结果，**必须看** |
| `bsp_cst816s_keepalive()` | 重新写一次"关自动休眠"，由上层周期性调用 |
| `bsp_cst816s_get_fault(out)` | 取最近一次失败的现场 + 累计的总线异常计数，见《失败现场》一节 |

返回值故意把两类失败**分开**，这是排错时最有用的一条信息：

| 返回码 | 含义 | 该查什么 |
|---|---|---|
| `BSP_CST816S_OK` (0) | 正常 | — |
| `BSP_CST816S_ERR_I2C` (-2) | I2C 通信本身失败 | **接线**：SDA/SCL 有没有接反、上拉、3V3、共地 |
| `BSP_CST816S_ERR_CHIPID` (-3) | I2C 通了，但 ID 不是 CST816 系列 | **型号**：接线没错，是芯片不对（或地址不对） |
| `BSP_CST816S_ERR_PARAM` (-1) | 传了空指针 | 调用方的问题 |

区分 `ERR_I2C` 和 `ERR_CHIPID` 的意义在于：这两个错误的**排查方向完全相反**。
一个是拿万用表量线，一个是回去翻型号手册。合并成一个 "初始化失败" 只会
让人从零开始猜。

## 用法

```c
bsp_cst816s_touch_t t;

if (bsp_cst816s_init() != BSP_CST816S_OK) { /* 看错误码，见上表 */ }

for (;;) {
    if (bsp_cst816s_read(&t) == BSP_CST816S_OK && t.pressed) {
        printf("%u, %u  gesture=%u\n", t.x, t.y, t.gesture);
    }
}
```

调用前必须先执行 `MX_GPIO_Init()`。`MX_I2C1_Init()` 保持调用不变
（`main.c` 里现有顺序就行）——驱动会 `HAL_I2C_DeInit()` 把 PB6/PB7
从复用模式解出来，那之后 I2C1 外设跟这条总线再无关系。

> **驱动吐的是原始坐标，不带任何方向逻辑。** 这是有意的：
> 方向变换全部集中在 [lv_port_indev.c](../UI/Src/lv_port_indev.c) 顶部的
> 三个宏里。这样"驱动读错了"和"方向反了"是两个能分开判断的问题——
> 混在一起就只能靠猜。

## 寄存器与坐标格式

从 `0x01` 起连读 6 个字节：

| 偏移 | 寄存器 | 内容 |
|---|---|---|
| 0 | `0x01` | 手势码 |
| 1 | `0x02` | 手指数，**为 0 就是没触摸** |
| 2 | `0x03` | X 高 4 位（低 4 位无效） |
| 3 | `0x04` | X 低 8 位 |
| 4 | `0x05` | Y 高 4 位（低 4 位无效） |
| 5 | `0x06` | Y 低 8 位 |

坐标是 12 位，所以要 `((高 & 0x0F) << 8) | 低`。
`0x02` 为 0 时直接返回"未按下"，省掉一次坐标拼装。

`0xA7`（ChipID）：`0xB5` = CST816S，`0xB6` = CST816T。
代码里接受 `0xB4 ~ 0xB7` 整个范围，因为这两颗芯片还有 S/T 之外的尾缀变体。

## ⚠️ 自动休眠 —— 不接 INT 的必踩坑

> ### 先说清楚：这一节讲的**不是**本工程实际遇到的那个卡死
>
> 下面这段描述的症状（"能用一阵子，然后永久按不动，时间不固定"）
> 和本工程实测到的现象**一模一样** —— 我一开始就是照它去查的，
> **查错了方向**。
>
> 实测的分界线是自检界面上的 `as=`：
> - `as=FAIL` → 关自动休眠没写进去 → **就是这一节说的问题**
> - `as=OK` 却照样卡死 → **不是这一节的问题**，去看「为什么改成软件模拟」那一节
>
> 本工程遇到的是后者（`as=OK` 也卡，而且 `e5` 在涨、`er=20 BUSY`）。
>
> **教训：症状一样不等于根因一样。** 一个症状能同时对上两个根因的时候，
> 必须找一个能把它们分开的量（这里就是 `as=` 和 `e5`），
> 而不是挑那个"听起来最像"的去改。

根因是 CST816S 上电默认**开**着自动休眠：

1. 从**最后一次触摸**开始计时，一段时间不碰，芯片进低功耗
2. 低功耗状态下它停止更新触摸寄存器，改为靠 **INT 引脚**通知 MCU
3. 本工程没接 INT（为了少一根线），所以**它睡下去之后轮询永远读不到手指**
4. 时间不固定，是因为计时从"你最后一次碰它"开始 —— 你碰得越勤，
   它睡得越晚

**为什么特别难查**：I2C 是好的、程序没卡死、坐标也算得对，
所有"看起来该查的地方"都是正常的。唯一的线索是它"能用一会儿再停"。

**解法**（两层保险，都在代码里了）：

| 层 | 做法 | 位置 |
|---|---|---|
| 第一层 | init 时写 `0xFE = 0x01` 关掉自动休眠，**并检查返回值** | `bsp_cst816s_init()` |
| 第二层 | 每 500ms 重写一次，防止芯片复位或毛刺让它退回默认值 | `bsp_cst816s_keepalive()`，由 [lv_port_indev.c](../UI/Src/lv_port_indev.c) 调用 |

> **第一层的返回值一定要看。** 之前那版把 `HAL_I2C_Mem_Write` 的返回值丢掉了，
> 理由是"写不进去顶多是芯片会睡"—— 结果就是卡死的时候完全无从判断
> 是没写进去还是别的原因。一个被丢掉的返回值，等于一条被主动删掉的线索。
> 现在用 `bsp_cst816s_autosleep_rc()` 取出来，自检界面上的 `as=` 就是它。

**另一种解法是接 INT 引脚**，让芯片睡着时能主动叫醒 MCU。
但那要配 EXTI、改中断处理，而且低功耗下寄存器不更新这一点还在，
只是换了个唤醒途径。先用保活把问题解决掉，等真要进低功耗模式再说。

## 排错时最有用的东西：6 个原始字节

`bsp_cst816s_touch_t.raw[6]` 是从 `0x01` 起连读到的原始字节，一字不改。
**坐标和按下状态都是这 6 个字节算出来的**，所以当触摸"莫名其妙不动了"的时候，
直接看这 6 个字节就能定性：

| `rc` 那行的样子 | 说明 |
|---|---|
| `rc 00 00 00 00 00 00` | 芯片在说"没手指" —— 是芯片的问题，**不是驱动算错了** |
| `rc 00 05 .. .. .. ..` | 手势寄存器有值但手指数是 0，说明芯片醒着且感知过手势 |
| 第 2 个字节非零、坐标却不合理 | 驱动解析的问题，回去看上面的位域格式 |

不看这几个字节，就只能对着算出来的 `x`/`y` 猜 ——
而"芯片说没手指"和"驱动把有手指算成了没手指"这两件事，
排查方向完全相反。

> **⚠️ 这 6 个字节只在"这次读成功了"的时候才算数。**
> `bsp_cst816s_read()` 读失败时会直接返回，**不会碰 `out->raw[]`**，
> 所以调用方如果不清，拿到的就是上一次成功读的残值。
> 残值会造出"第 2 字节说有一根手指、状态却是抬起"这种自相矛盾的组合，
> 看起来像芯片报了个怪状态，其实是过期数据 —— 照它去查会把方向整个带偏。
> 上层 [lv_port_indev.c](../UI/Src/lv_port_indev.c) 的做法是失败时
> 把 `raw[]` 连同 `raw_x` / `raw_y` / `gesture` 一起清零，
> 并用 `read_ok` 标志让界面显示 `--` 而不是旧值。

## 失败现场：`bsp_cst816s_fault_t`

只记一个"失败了多少次"是不够的。一次传输有十几个可能断掉的地方，
合并成一个计数器就等于把唯一能定位的东西扔了。软件模拟之后，
可以精确到**断在哪一拍**：

| `phase` | 界面显示 | 含义 |
|---|---|---|
| 0 | `--` | 没失败过 |
| 1 | `STUCK` | **传输还没开始，总线就被占着** |
| 2 | `START` | 发不出 START（拉低 SDA 后 SCL 没跟着确认） |
| 3 | `ADDR` | 地址字节没被应答 —— 芯片没理我们 |
| 4 | `REG` | 寄存器号没被应答 —— 地址认了，寄存器不认 |
| 5 | `DATA` | 数据字节没被应答（写寄存器时） |
| 6 | `SCL` | 等 SCL 放开超时 —— 从机在做**时钟拉伸**且不放手 |

这张表比 HAL 的 `HAL_BUSY`/`HAL_TIMEOUT` 有用得多：`ADDR` 和 `REG`
在 HAL 那套里都只会报 `AF`，但一个是"地址错了/芯片没上电"，
另一个是"协议对上了但寄存器不支持"，排查方向完全不同。

`scl_level` / `sda_level` 是失败那一刻两条线的实际电平（1 = 高）。
**空闲的 I2C 总线两条线都该是高**，所以谁被拉着不放，谁就是卡住的那一方。
界面上显示成 `SC0` / `SD0`（只在低的时候显示）：

| 现场 | 说明 | 救得回来吗 |
|---|---|---|
| `SC0`（SCL 低） | 从机在做**时钟拉伸**而且不放手 | 打时钟没用（拉伸协议上可以无限长），**只能靠 RST** |
| `SD0`（SDA 低） | 从机停在半个字节中间，在等时钟 | 打 9 个时钟能让它走完当前字节 |
| 两个都不显示 | 两条线都是高的 → **电气上总线是空闲的** | 问题不在线上 |

对 `START` 失败这一格来说，`SC0`/`SD0` 是**唯一**的线索：
`bus_start()` 失败只有两种原因 —— SCL 升不起来（从机在拉伸）
或者 SDA 被抱着放不开（建不出下降沿）。这两种的下一步处置完全相反，
而电平正好把它们分开。

> 这也是为什么采现场必须**在 `bus_stop()` 之前**：`bus_stop()` 会把
> SDA 拉低再放开，收完尾两条线必定是高的，那时候再采，
> `SC0`/`SD0` 永远是"两个都不显示"，这条线索就白丢了。

### 两个累计计数器

`phase` / `scl_level` / `sda_level` 是**最近一次失败**的快照，
另外两个是**累计**的，跟这一次成没成功无关：

| 字段 | 界面 | 含义 |
|---|---|---|
| `bus_stuck` | `bs=` 左边 | 开始传输时总线不是空闲状态的次数 |
| `unwedge_failed` | `bs=` 右边 | 打了 9 个时钟之后线还是没放开的次数 |

> **⚠️ 这两个数在读成功的时候也会涨，所以必须每帧都取一次。**
>
> `bus_stuck` 最常见的形态恰恰是"总线被占住 → 打时钟救回来 → 这次读成功"。
> 只在失败分支里取的话它永远是 0 —— 而它正是判断
> 「有没有东西在物理上拉着线」的唯一依据。这个坑我踩过。

`bsp_cst816s_get_fault()` **不碰总线、不改状态**，读的是刚存下来的快照，
所以可以在任何地方、任何频率调用。

> 顺带一提，早先用外设那版还有"只记一串失败的头一帧、后续帧不覆盖"的讲究
> —— 因为外设卡住之后会一直刷同一个状态，只有头一帧有信息量。
> 软件模拟没有这个问题：**每一次传输都是独立的，最近一次就是现在正在发生的**，
> 所以那套"武装/解武装"的复杂度整个删掉了（连同只服务它的
> `bsp_cst816s_bus_recover()`）。

## 总线卡死 —— 为什么重试没有用

**这一节是整件事的关键，值得完整读一遍。**

### HAL 在超时之后不会收拾现场

看 `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_i2c.c` 里的
`I2C_WaitOnFlagUntilTimeout()`（本工程用的是 1.28.x 前后的版本），
等标志位超时之后它做了三件事：

1. 把软件状态标成 `HAL_I2C_STATE_READY`
2. 把 `ErrorCode` 或上 `HAL_I2C_ERROR_TIMEOUT`
3. `return HAL_ERROR`

**它不产生 STOP，也不去清 `SR2` 的 BUSY 位，更不会复位外设。**

（`I2C_WaitOnMasterAddressFlagUntilTimeout()` 也一样：只有 AF 置位那一路
会补一个 STOP 并清 AF，超时那一路什么都不补。）

### 于是失败会自我维持

```
某次传输卡住（起因不明，可能只是一次时序意外）
        ↓
HAL 超时返回，把烂摊子留在总线上：BUSY 一直挂着
        ↓
下一次调用 → 在"忙"的总线上发 START → 又卡住
        ↓
再超时返回，BUSY 还挂着 → ……
```

这是个**自我维持的循环**。所以症状不是"偶发失败攒够了次数"，而是
**一次失败之后就再也回不来了** —— 表现就是「用一阵子，然后永久按不动了」。
重试再多也没用，因为每次重试都在加深同一个死锁。

### 第一版修复：在外面打补丁（失败）

顺着上面这个分析，最自然的结论是"那就主动收场"——写一个
`bsp_cst816s_bus_recover()`：`HAL_I2C_DeInit` 把引脚解出来 → 配成开漏 →
打 9 个 SCL 时钟让从机走完当前字节 → 补一个 STOP → 检查线放开没有 →
重新 `MX_I2C1_Init()` → 硬件复位芯片 → 重写 `0xFE=0x01` 把自动休眠再关一遍。

按源码推演这套是能救回来的，**实测却每次都失败**：自检界面上的 `b`
（恢复失败的次数）一直在涨，说明打完时钟线还是没放开。

到这一步按"连续 3 次修复失败就质疑架构"的规矩停下来了。回头看，
真正的问题不在恢复函数写得对不对，而在**它是跑在那个外设之外的**：

外设一旦把 BUSY 挂上，它就对"外面把线救回来了"这件事毫无感知。
恢复函数能做的最多是让**线**回到空闲，然后祈祷外设的状态机也跟着
回到空闲 —— 而这一步没有任何办法保证。

### 第二版：把外设从这条路上拿掉

所以最后没有继续打补丁，而是换了**传输层**：PB6/PB7 当普通开漏 GPIO 用，
自己翻转电平，`HAL_I2C_DeInit()` 之后再也不碰 I2C1 外设。

换过来之后，"卡住"这件事的**性质**变了，而不只是概率变了：

| | 外设（HAL） | 软件模拟 |
|---|---|---|
| 卡住时的状态 | 停在 `BUSY` 上 | 没有状态可停 |
| 持续时间 | **永久**，只能靠复位外设救出来 | 最多一次传输 |
| 怎么恢复 | 需要一个专门的恢复函数 | 不需要 —— 下一次调用就是一次全新的传输 |
| 恢复函数失败会怎样 | 死锁继续 | 不存在这个函数 |

上面那个"自我维持的循环"之所以成立，前提是**有一个会被卡住的状态机**。
每次等待都改成有上限计数的循环之后，这个前提没有了：
最坏情况是这一帧读失败，下一帧从一条空闲的总线上重新开始。

> 我说"永久卡死在这个结构下不可能发生"，指的是**这一类**故障
> —— 即"某个状态位卡住导致后续所有操作必然失败"。
> 它不保证 I2C 一定读得通：线接错了还是读不通，只是症状变成
> "每一帧都失败且 `phase` 明确"，而不是"用一阵子之后永久按不动"。

代价是每次读多花 **2.2~3.2ms** CPU。约 45kHz 的软件时序下，一次 6 字节读
是 204~289 个半位 —— 下限 204 是"放开 SCL 它立刻就升起来"的理想情况，
实际每处 `scl_wait_high()` 通常要多等一个半位再采样，所以真值靠近 289。
在 33ms 的轮询周期里占约 10%。半位的构成和提速的办法，
见 [bsp_cst816s.c](Src/bsp_cst816s.c) 里 `CST816S_BIT_DELAY_LOOPS` 的注释。

**保留下来的一件事**：打 9 个时钟解锁从机的逻辑还在，但降级成了
`bus_prepare()` 里的一行 —— 只在**开始传输时发现总线不是空闲**才打，
而且打完之后**这次传输就正常往下走**，不额外做复位、不重写寄存器。
计数记在 `bus_stuck` / `unwedge_failed` 里，见上一节。

> **为什么不能直接把 SDA 拽高**：总线上的 SDA 现在可能同时被 MCU 和从机
> 拉着。硬推高就是两个输出对打，轻则拉不上去，重则烧引脚。打时钟是
> 「请求」从机放手，符合协议。

### 为什么软件模拟不会挂死

关键在于**每一处等待都有上限**，而且上限是"多少个半位时间"这种
可算的量，不是 `HAL_Delay` 那种"至少 1 个 tick、相位不巧翻倍"的东西：

| 等待 | 上限 | 超时后 |
|---|---|---|
| 等 SCL 放开（防时钟拉伸挂死） | `CST816S_LINE_WAIT_LOOPS` = 200 个半位 ≈ 2.2ms | 记 `SCL` 阶段，收 STOP 返回失败 |
| 等总线空闲（传输前） | `CST816S_IDLE_SETTLE_LOOPS` = 8 个半位 ≈ 88µs | 打 9 个时钟解锁，再等一次；还是不行就记 `STUCK` 阶段返回失败 |
| 一个半位多长 | `CST816S_BIT_DELAY_LOOPS` = 100 圈 | 不等待，纯延时 |

**单次调用最坏阻塞多久**（这是"会不会影响界面流畅度"的答案）：

| 情况 | 耗时 |
|---|---|
| 正常读一次 | 2.2~3.2ms |
| 数据阶段超时 | 3.2ms 已完成的工作 + 2.2ms（超时的那次等待）+ 2.2ms（收尾的 STOP）= **约 7.6ms** |
| `bus_start` 失败 | 2.2ms（等 SCL）+ 2.2ms（补 STOP）= **约 4.4ms** |
| 总线被占（`bus_prepare` 失败） | 88µs × 2 + 解锁的 198µs = **约 0.4ms** |

也就是说最坏一帧约 **7.6ms**，仍然远小于 33ms 的轮询周期，
不会把界面卡出可感知的顿挫。`bus_stop()` 里那次 `scl_wait_high()`
是中间两行的大头 —— 它平时只花一个半位（`scl_release()` 之后
立刻采样，线还没升上去，要再等一拍），只在"从机真的把 SCL
拉住不放"这个故障路径上才吃满 2.2ms。

另外，**`volatile` 计数器让这个时序和优化等级无关**。
实测 `-O0` 和 `-O3`（Keil 的 `<Optim>4</Optim>`）编出来，
循环体都是"读内存-加一-写内存-比较"共 11 个周期 ——
编译器必须真的跑这个循环，不能把它优化掉。这一点很重要：
如果哪天换编译器/优化等级导致时序变成 1MHz 以上，
在长线 + 弱上拉上必然出错，而这种错误极难查。

（顺带一提：I2C **没有最低频率限制**，所以"慢"永远是安全的。
上面那个 45kHz 是刻意选的保守值。）

## 调不通怎么查

按 `bsp_cst816s_init()` 的返回码分两路：

**返回 `ERR_I2C`（-2）——线的问题**
1. 量 PB6/PB7 到模块的通断，确认 SDA/SCL 没接反
2. 量 SDA/SCL 对 3V3 的静态电压，应该是 3.3 V（被上拉）
3. 量模块 VCC 和 GND，确认共地
4. 上拉不够就加 4.7 kΩ，见上文
5. 都对了还是不行，看自检界面的 `phase` 字段定位断在哪一拍：
   - `ADDR` → 地址字节没被应答，芯片没理我们（没上电 / 接反 / 地址不对）
   - `REG` 或 `DATA` → 地址认了，寄存器不认，说明**芯片型号不对**
   - `SCL` → 从机在做时钟拉伸且不放手
   - `START` → 线接反或没接
   - 什么都不显示但错误在涨 → 两条线电平都正常，那是别的问题

> 以前这里写的是"用 `HAL_I2C_IsDeviceReady()` 单独确认地址上有没有设备"。
> 现在那个办法不能用了 —— 驱动在 init 里就把 I2C1 外设 DeInit 掉了。
> 而且也没必要：`phase` 已经把同样的信息说得更细。

**返回 `ERR_CHIPID`（-3）——芯片的问题**
线是通的，所以别再量线了。查：
1. 模块是不是 CST816 系列（有些商家拿 GT911 / FT6236 冒充）
2. 芯片的 I2C 地址对不对——`0x15` 是 CST816 的 7 位地址，
   代码里左移一位变成写地址 `0x2A` / 读地址 `0x2B`，
   这个换算在 [bsp_cst816s.c](Src/bsp_cst816s.c) 的
   `CST816S_ADDR_WRITE` / `CST816S_ADDR_READ` 里

**`init` 返回 OK，但 `read` 从来没有 `pressed`**
说明复位和 ID 都过了，线是好的。看自检界面：
1. 先看 `as=` 是不是 `OK`。是 `FAIL` 就是关自动休眠没写进去，芯片会睡，
   见上面「自动休眠」一节
2. 再看 `rc` 那 6 个字节。第 2 个字节恒为 0 = 芯片一直在说"没手指"，
   那就是面板本身的问题（芯片到面板的排线、或者触摸板是独立的没贴在屏幕上）
3. `n` 不涨的话跟驱动无关，是 LVGL 那侧没调 `read_cb`

**能用一阵子，然后突然按不动了（时间不固定）**

这个症状有**两个**可能的根因，而且它们指向相反的修法，
所以不要猜 —— 按下面的顺序分开：

1. **先看 `e5`（最近 5 秒的失败次数）**
   - `e5` **在涨** → 此刻 I2C 就是坏的。这条路要查的是总线：
     看失败现场那行的 `phase`（`STUCK`/`START`/`ADDR`/`REG`/`DATA`/`SCL`）
     和 `SC0`/`SD0`，对照上面「失败现场」一节的表。
     **这时候别去查芯片休眠，方向是反的。**
   - `e5 = 0` → 此刻 I2C 是好的（此时驱动仍在正常读数），继续往下走。

2. **看 `n=` 还在不在涨** —— 在涨说明程序没卡死、`read_cb` 一直在跑。

3. **看 `rc` 那 6 个字节** —— 应该是 `rc 00 00 00 00 00 00`，
   芯片在说"没手指"。

4. 三条都符合（`e5=0`、`n` 在涨、`rc` 全 0）**才是**自动休眠，
   见上面「自动休眠」一节。

5. **看 `bs=` 那个数在不在涨** —— 它在涨说明有东西在物理上拉着总线，
   被 `bus_prepare()` 的 9 个时钟救回来了（`bs` 右边那个数记的是没救回来的次数）。
   老是涨就不是偶发，去量线。

> **历史教训（两个假设都是猜错的）**
>
> 最初只有「自动休眠」一个假设，因为症状（"刚开始能用、过一会儿停、
> 时间不固定"）和它完全吻合 —— 结果实测 `as=OK`（关休眠确实写进去了）
> 却照样卡死，假设被推翻。
>
> 然后猜「上拉不足 / 信号完整性」，理由是 `e` 从 0 涨到 63 说明 I2C 在批量失败。
> 结果实测 `er=20`（只有 TIMEOUT，**没有** `BERR`）—— 没有 BERR 就意味着
> 没有电气毛刺，这个假设也被推翻。
>
> 真正的转折是去读 HAL 源码，而不是继续从症状猜。读出来的是：
> HAL 超时之后不产 STOP、不清 BUSY，所以失败会自我维持。
> **症状一样不等于根因一样** —— `e5`、`bs`、`phase`、`SC0`/`SD0` 这几个量
> 就是为了不再靠症状猜而加的。
>
> 而最后落地时也没有去"修"那个外设，而是把它整条从路上拿掉 ——
> 见上面《第二版：把外设从这条路上拿掉》。

**方向不对（坐标对，但位置镜像/旋转）**
这不是驱动的问题，改 [lv_port_indev.c](../UI/Src/lv_port_indev.c) 顶部的
`TOUCH_SWAP_XY` / `TOUCH_MIRROR_X` / `TOUCH_MIRROR_Y`。判断方法见
[UI/README.md](../UI/README.md)。

## 一个已知的重生成陷阱

`HAL_I2C_MspInit()` / `HAL_I2C_MspDeInit()` 写在
[i2c.c](../Core/Src/i2c.c) 里，**不是** `stm32f4xx_hal_msp.c`。
这是跟着本工程已有的惯例走的（`HAL_SPI_MspInit` 就在
[spi.c](../Core/Src/spi.c) 里）。

但 CubeMX 默认把外设 Msp 生成到 `stm32f4xx_hal_msp.c`。
所以**如果回 CubeMX 重新生成代码，会出现两份 `HAL_I2C_MspInit`，链接报重复符号**。
届时把 `stm32f4xx_hal_msp.c` 里新生成的那份删掉即可（SPI 同理）。
不影响当前编译——当前工程里 `stm32f4xx_hal_msp.c` 只有全局的 `HAL_MspInit`。
