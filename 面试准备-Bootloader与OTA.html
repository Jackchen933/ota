INTERVIEW QUEST

Bootloader 与 OTA 面试特训

你会的是流程，面试官听的是话术。本页把项目代码翻译成「先说什么 → 再说什么 → 必点哪些词 → 哪些回答会死」。
原则：每句话都要能落到代码；落到代码的每句话都要敢被追问三层。

LEVEL 1

开场60秒：项目介绍定生死

面试官
简单介绍一下这个项目吧。
回答骨架（背下来，60秒内讲完）：
  • 一句话定位：这是一个完整的设备端 OTA 升级系统——Bootloader 和 App 双工程独立开发联调，实现设备在业务不中断的情况下后台完成固件升级。
  • 一句话链路：全链路是「App后台下载密文到外部Flash → 置标志复位 → Bootloader解密搬运校验 → 新固件试用期验证 → 通过才备份转正，失败自动回滚」。
  • 两个亮点预埋（引面试官来问，别一口气讲完）：一是升级标志的掉电安全设计，二是看门狗试用期+自动回滚，升级失败不变砖。
  • 角色收尾：Bootloader 和 App 两侧都是我独立完成的。
死亡回答：
  • 从Ymodem帧格式开始讲细节——开场要给全景，细节留给追问。
  • "我做了Ymodem移植、写了Flash驱动、调了DMA……"——流水账，没有架构感。
  • 超过90秒——面试官失去耐心，后续全在打断中崩盘。
面试官
整个流程再走一遍？上电之后发生了什么？
回答骨架（画图讲，边说边画状态机）：
  • 上电先进 Bootloader（它在 Flash 最前面 0x08000000，硬件决定绕不开），读标志扇区里的 App 运行状态，五路分发。
  • 0x44 有效App → 直接跳 App（日常开机，毫秒级，感知不到）。
  • 0x11 下载待更新 → 子流程A：读密文大小→擦运行区→从外部Flash下载区边解密边搬运→MD5比对→通过置 0x22 复位。
  • 0x22 验证新App → 子流程B：开 IWDG → 跳 App 试用期（App自检通过置 0x33 再复位）；如果这次复位是看门狗造成的 → 直接转回滚。
  • 0x33 备份 → 子流程E：把下载区密文复制到备份区 → 置 0x44 转正复位。
  • 其他/空白 → 路径D：备份区有效就回滚，否则待机等按键 Ymodem 刷机。
加分动作：画完图补一句"这套状态机的核心思想是每一步都可以安全地重来——任何时刻掉电，标志扇区里的状态都对应一条确定的恢复路径"。面试官听到这句就知道你懂掉电安全。
LEVEL 2

分区与跳转

面试官
分区怎么设计的？为什么这么划？
回答骨架：
  • 先报芯片底账：F411 共 512KB，Flash 扇区非均匀——前4个16KB、1个64KB、后3个128KB。
  • 内部三段：Bootloader 32KB（扇区0-1，放小扇区擦得快）、标志扇区16KB（扇区2，独立出来是因为改标志要整扇区擦，绝不能和App混在扇区里互相擦掉）、App运行区464KB（扇区3-7）。
  • 外部 W25Q64 两段：下载区A 512KB（新固件密文）+ 备份区B 512KB（验证通过的旧固件备份）。放外部是因为内部空间不够双份，且外部Flash写不占用内部总线。
  • 收尾：App 链接起始地址 0x0800C000、大小受限 0x74000，向量表偏移 0xC000，三处同步改。
死亡回答："按流程图划的"——面试官要听的是约束推导：为什么标志扇区必须独立、为什么备份放外部，答不出推导就露馅。
面试官
从 Bootloader 跳到 App 具体做了什么？
回答骨架（背跳转五步，顺序不能乱）：
  • ① 校验：App 向量表第0项（栈顶指针）要指向 RAM 区间，否则不跳。
  • ② 跳前喂狗：IWDG 一旦开启关不掉，跳过去到 App 接管前有几秒空窗，先把计数拉满。
  • ③ 关外设、关中断：尤其停掉呼吸灯定时器——它的中断每50µs改写LED引脚，不关会持续打断 App。
  • ④ 向量表重映射到 App 起始地址（0x0800C000）。
  • ⑤ 取 App 向量表第0项设 MSP，取第1项当复位向量跳过去。
为什么这样做：跳转本质是"软件伪造一次复位后的取指"——复位后 CPU 做的就是读0x0800C000处的栈顶和复位向量。谁先设置MSP、谁关中断，一步都不能省，省了就是 HardFault。
面试官
追问：App 里为什么还要再设一次向量表？
回答：Bootloader 设置的向量表只保证跳转那一刻取指正确；App 跑起来一旦发生中断，硬件固定从 VTOR 指向的表取向量。App 在 system 启动文件里把 VECT_TAB_OFFSET 设成 0xC000，让所有中断都进 App 自己的中断服务函数——漏了这步，中断会跳进 Bootloader 的表，直接跑飞。
LEVEL 3

标志扇区状态机（掉电安全核心）

面试官
升级标志为什么放在内部Flash独立扇区？用EEPROM不行吗？
回答骨架：
  • 候选方案三个：EEPROM、外部Flash、内部Flash独立扇区。
  • 选内部扇区的理由一：上电第一时刻就能读——内存映射直接解引用，不用先初始化I²C/SPI，Bootloader越早知道走哪条路越好。
  • 理由二：和App天然共享——Boot和App是两个独立工程，都要读写同一份标志，放双方都"看得见"的固定地址最内聚。
  • 代价诚实说：内部Flash擦除粒度大（16KB整擦）、寿命1万次比EEPROM的100万次短——所以升级标志这种低频写的数据合适；高频记录（App大小统计）才放EEPROM。一句话：按写频率和数据归属选存储介质。
面试官
原码+反码双写是什么意思？为什么要这么干？
回答骨架：
  • 每个关键字段存两份：原码 + 按位取反的反码。读取时校验 原码 XOR 反码 == 0xFFFFFFFF 才算有效。
  • 防两类事故：写一半掉电（只写出了原码，反码还是0xFF，校验必失败）和位翻转/存储损坏（随机错一位，双份同时错且保持互补的概率约 1/2^32）。
  • 失败后的处理是宁可信其无：字段清零当作无效——状态机回落到路径D待机，宁可让用户多刷一次机，也绝不拿一个可疑的标志去擦Flash。
死亡回答："为了防止数据出错"——没说出XOR校验方法、没说失败后的策略，等于没答。
面试官
写标志写到一半掉电，系统会怎样？
回答骨架（这是全项目最值钱的问题，慢点答）：
  • 先说写入策略：标志整个扇区只在RAM里改镜像，改完一次性「整扇区擦除→逐字写回→读回比对」，原子落盘——不存在"改了A字段没改B字段"的中间态。
  • 再讲时序设计：先动数据、后置标志。比如下载完成：先把密文全部落盘到外部Flash，最后一步才写"下载待更新"标志——中途任何时刻掉电，标志都没置上，Bootloader把这次下载当不存在，旧固件照常跑。
  • 收尾总结：整个状态机的每条转换边都满足"标志未落盘=事情没发生"，所以任何时刻掉电都有确定的恢复路径。
为什么这样做：掉电安全的本质不是"防掉电"（防不住），而是让每个中间状态都可解释、可恢复。这句话可以直接说给面试官。
LEVEL 4

Ymodem 与双线程传输

面试官
Ymodem 协议大概是个什么流程？
回答骨架（讲三段就够）：
  • 握手：接收方周期发'C'请求CRC模式；发送方回首帧（文件名包）——文件名+空格+文件大小，接收方从这里拿到密文包总长，据此算要擦哪些扇区。
  • 数据流：1024字节数据帧连续下发，每帧尾带CRC16；收对了回ACK，错了回NAK让发送方重传这一帧。
  • 结束：EOT→ACK→结束帧→ACK，收尾把总大小写进标志扇区置升级请求。
加分动作：主动补一句"我做过Ymodem的发送方向，把App固件回传给上位机做过回读校验"——收发两侧都摸过的人极少，差异化立刻出来。
面试官
串口接收为什么用DMA空闲中断？不用行不行？
回答骨架：
  • 三个候选：轮询（CPU空转，业务全停）、逐字节中断（115200bps下每87µs进一次中断，10KB固件就是几十万次中断，把业务线程活活打死）、DMA+空闲中断。
  • DMA空闲中断的机制：DMA在后台把字节搬进环形缓冲，CPU完全不参与；一帧数据发完总线空闲，硬件触发IDLE中断，CPU才一次性来处理整块。
  • 效果：中断次数从"每字节一次"降到"每帧一次"，App业务线程几乎无感——这就是"无感升级"里"无感"两个字在传输层的落点。
面试官
为什么收包和写Flash要拆成两个线程？
回答骨架（必考，考的是RTOS素养）：
  • 矛盾点：速率不匹配——串口收一块是毫秒级，写外部Flash擦一个扇区是百毫秒级。单线程边收边写，收包缓冲必然溢出丢包。
  • 解法：接收线程收满一块就投进消息队列立刻回去收下一块；落盘线程慢慢从队列取块写Flash。队列深度=缓冲块数，每块交出前先take掉占用，所以队列在逻辑上永远不满，溢出不可能发生。
  • 这就是生产者-消费者模型：用空间换时间，把快收和慢写解耦。
死亡回答："为了架构清晰"——没说出速率不匹配这个矛盾，等于白设计。追问"队列满了怎么办"时答"丢弃"也死——正确答案是我的设计里队列逻辑上不会满，同时启动阶段要先排空残留数据。
LEVEL 5

AES 加密与双层校验

面试官
固件为什么要加密？整个校验体系是怎么分层的？
回答骨架（先分层再讲各自管什么）：
  • 加密的目的：固件是产品核心资产，串口明文传输等于裸奔；AES-256-CBC保证被抓包也拿不到固件。
  • 校验分两层：CRC16管帧级——串口传输的随机误码，快，够用；MD5管文件级——整个固件对不对、有没有被篡改。
  • 一句话总结分工：CRC防"不小心坏"，MD5防"被人动过手脚"，两层缺一不可。
面试官
MD5 怎么比？和谁比？为什么放包尾？
回答骨架：
  • 密文包格式：16字节加密头 + 固件密文 + 16字节MD5指纹（指纹是打包时对固件明文算好、明文附在包尾的）。
  • 搬运时Bootloader边解密边把明文喂给MD5，搬完得到自己的指纹，和包尾预留的做memcmp。
  • 放包尾三个理由：位置确定（总长-16一算就到）；搬完数据刚好读到，天然形成"收尾即比对"的时序；和数据连成一个完整文件，一次传输搞定。
  • 最关键的认知：这一次比对同时验证了三件事——密文没坏、密钥正确、解密无误。任何一件出问题，解出来就是乱码，指纹必对不上（概率1-1/2^128）。
面试官
追问：AES密钥放在哪？会不会被抓包或者从固件里逆向出来？
回答（诚实+展示认知深度，这题答"藏得很好"必死）：
  • 现状诚实讲：密钥以数组形式内置在固件里，流程图设计的是从加密芯片读取密钥，我这版是软件模拟的占位实现。
  • 然后展示思路：内置密钥挡得住抓包、挡不住逆向（bin里能搜出来）；生产级方案是密钥放独立加密芯片或安全单元，Flash里只存密文，攻击者拿到固件镜像也拿不到密钥。
  • 收尾："所以架构上我把密钥获取抽成了独立一步，换真芯片只改密钥来源，流程不动。"——把缺陷讲成架构预留，这是最体面的答法。
LEVEL 6 · BOSS

看门狗试用期与自动回滚（最亮的一张牌）

面试官
你的方案里固件校验通过了就敢直接跑吗？怎么保证新固件本身没问题？
回答骨架（把试用期机制完整讲出来）：
  • 先点破认知：MD5通过只能证明"搬运正确"，不能证明"固件能跑"——代码里有bug照样让设备变砖。
  • 所以中间插了一个"试用期"状态：搬运成功置"验证新App"，下次复位Bootloader开IWDG再跳转——限时试跑。
  • App自检通过（验向量表合法性）→ 置"备份"标志复位，Bootloader备份转正；App跑挂 → 没人喂狗，8.2秒后IWDG咬复位。
  • 点睛：App自检失败的处理是故意躺平不喂狗——让看门狗来复位，把"固件坏了"翻译成"一次看门狗复位"。
面试官
复位之后 Bootloader 怎么知道"上次是固件跑挂了"而不是正常开机？
回答骨架（这是全项目最精妙的一环）：
  • 线索在复位原因寄存器 RCC->CSR 的 IWDGRST 标志位：看门狗复位后这个位会被硬件置1。
  • Bootloader上电第一件事读它：标志="验证新App" 且 IWDGRST=1 → 两个条件同时成立 = 新固件没活过试用期 → 不跳了，转回滚流程，从备份区恢复旧固件。
  • 细节加分：读完必须RCC_ClearFlag清掉——这个位是写一清除，不清会一直残留，下次正常开机被误判成"又是狗咬的"。
  • 总结句："新固件只有一次试用期机会，挂了就永久回滚——这就是升级失败不变砖的保证。"
死亡回答："加个计数器记录失败次数"——放哪记？掉电丢不丢？多绕远路。复位原因寄存器是硬件白送的，用硬件方案永远优先于软件方案。
面试官
IWDG 和 WWDG 有什么区别？为什么选 IWDG？
回答骨架：
  • IWDG独立看门狗：独立LSI时钟（32kHz），主时钟崩了照样跑；超时了直接复位；一旦开启关不掉。
  • WWDG窗口看门狗：用PCLK，必须在时间窗口内喂（早喂晚喂都复位），能产生中断做临终处理。
  • 选IWDG的理由：试用期要的是"活不过时限就复位"的强保证——App跑飞、死循环、时钟异常都要能兜住，IWDG独立时钟+不可关闭正合适；WWDG的窗口喂狗精细计时反而用不上，且系统时钟挂了它也跟着死。
  • 参数张口就来：LSI 32kHz÷64分频÷重装0x0FFF≈8.2秒；App初始化+自检几秒内完成，够用。
面试官
逐个环节说：哪里掉电会出问题？
回答骨架（拿表格逐行过，显出系统性）：
掉电时机后果与恢复
下载中标志未置，Boot当无事发生，旧App照常跑；外部Flash留半截密文，下次下载覆盖
搬运中运行区被擦了但标志还是0x11 → 复位后重走子流程A，从外部Flash重新搬（源数据还在）
写标志中原码+反码校验失败 → 当无效，回落路径D
试用期挂了IWDG咬复位 → IWDGRST+0x22 → 回滚备份区旧固件
备份中标志还是"备份中"未到0x44 → 复位重走备份（源在外部下载区，可重来）
收尾：所有路径的共同点是"源数据在动数据之前永不破坏"——外部下载区和备份区互相独立，运行区随便擦，都有地方重来。
LEVEL 7

高压追问与反问环节

面试官
用户在升级过程中拔了电池呢？你测过吗？
回答：上一页的掉电表格就是回答框架，但这题重点在测试方法论：真机上掉电注入测试——写个脚本在下载/搬运/写标志各阶段用继电器随机断电循环几百次，每次上电检查设备能否恢复到可用状态；再加坏包注入：手动改密文一个字节验证MD5拒绝、删反码字段验证标志失效、喂坏首帧验证Ymodem重传。"测过+怎么测的"远比"理论上没问题"值钱。
面试官
这个方案有什么不足？重新设计你会改什么？
回答骨架（展示成长型思维，缺点要说真的）：
  • 密钥管理：内置数组 → 换加密芯片/安全单元（已在架构里预留接口）。
  • 只防单次失败：断点续传没做，下载中断网要从头收——加断点记录（已收字节数落盘）可续传。
  • MD5防篡改够用但非密码学安全，高安全场景换 SHA-256 + 签名验签（ECDSA），公钥放设备、私钥放服务器。
  • 差分升级：全量包对低速信道太大，可上 bsdiff 差分包。
  • 收尾："这些不足我都清楚，且每一项的改进方向和改造成本都评估过"——把开放题变成展示工程判断力的机会。
面试官
你有什么想问我的吗？
