LEVEL 1

CRC 是什么：给一帧数据算个"余数"

▶

CRC（循环冗余校验）的本质：把整帧数据看成一个巨大的二进制数，用一个约定的"除数"去做除法，把余数当作校验值附在数据后面。接收方拿数据再除一遍，余数对不上就是传坏了。

你的项目里它长什么样

Ymodem 数据帧的尾部两个字节就是 CRC16：

┌──────┬──────┬────────┬──────────────────┬─────────┐ │ SOH/ │ 帧号 │ 帧号反码│ 数据 128/1024B │ CRC16 │ │ STX │ seq │ 255-seq│ ← CRC 只算这一段 → │ 高+低 │ └──────┴──────┴────────┴──────────────────┴─────────┘ 0x01 1B 1B 2B 0x02
■ 为什么用 CRC 不用普通"校验和"（把字节加起来）？

校验和太弱：两个字节同时坏、恰好互相抵消（+3 和 -3），校验和不变，错误就漏过去了。CRC 做的是多项式除法，对连续多位翻转（突发错误）的检测能力是数学证明过的——16 位 CRC 能保证检测出所有长度 ≤16 位的突发错误。传输线上最常见的恰恰就是连片误码。

你用的具体品种：CRC16-CCITT（XMODEM 变体）

参数值含义
生成多项式 G0x1021x¹⁶+x¹²+x⁵+1，做除法的"除数"（有效位17位：0x11021）
初始值0x0000余数寄存器从 0 开始（注意：不是所有 CRC 变体都是 0）
输入/输出反射否按字节高位在先处理，不搞位序翻转
结果异或0x0000算完直接用，不再异或
⚠ 品种不同 = 结果完全不同

同一个数据，CRC16/XMODEM、CRC16/MODBUS、CRC-CCITT(FALSE) 算出来的值互不相同——差异全在"初值 / 是否反射位序 / 结果是否异或"这三件配置上。Ymodem 协议用的是 XMODEM 变体，上位机和设备两端必须配同一品种，否则每帧都校验失败。

■ 中间结果

CRC 的核心操作只有一个：左移一位，顶出来了就异或多项式。全部字节滚完，寄存器里剩下的 16 位就是 CRC 值，高字节在前放进帧尾。

LEVEL 2

CRC 逐位手算：8 步滚完一个字节

▶

用最小例子完整走一遍：数据 1 个字节 0x31（ASCII 的 '1'），多项式 0x1021，初始值 0x0000。

代码只有 5 行

uint16_t crc16_xmodem(const uint8_t *d, uint32_t len) { uint16_t crc = 0x0000; /* 1. 余数寄存器清零 */ while (len--) { crc ^= (uint16_t)(*d++) << 8; /* 2. 字节放进寄存器高8位 */ for (int i = 0; i < 8; i++) { /* 3. 一个字节滚8次 */ if (crc & 0x8000) /* 4. 顶出来的是1 → 异或多项式 */ crc = (crc << 1) ^ 0x1021; else /* 顶出来的是0 → 只左移 */ crc <= 1; } } return crc; /* 5. 剩下的16位就是CRC */ }

0x31 的 8 步滚动手账

第 2 步后寄存器 = 0x3100（0x31 抬到高 8 位）。接下来滚 8 轮，每一轮只看最高位：

20x62000左移0xC400

80x13390左移0x2672
■ 中间结果

CRC16-XMODEM("1") = 0x2672。一帧 1024 字节就是把 1024 个字节连续滚 8192 轮，寄存器像一条传送带，前面的字节不断被"推挤"出去，最后整个数据都从寄存器里流过一遍。

数学本质：多项式除法（模 2 除法）

上面那 8 轮滚动，等价于一个竖式除法：数据左移 16 位后，除以生成多项式 0x11021，余数就是 CRC。"模 2"意思是减法不借位、加法不进位，全部用异或代替：

查表法：工程上的提速

逐位滚，1024 字节要 8192 轮循环。工程做法是预生成一张 256 项的表：把"每个字节值滚完 8 轮的效果"提前算好存起来，运行时每个字节只查一次表 + 一次异或：

crc = (crc << 8) ^ crc_table[(crc >> 8) ^ byte]; /* 一行顶八轮 */
■ 验证卡：两条独立路线复核你的实现

① 用上面 5 行代码跑 "123456789"，标准校验值 CRC16-XMODEM = 0x31C3——这是协议圈背下来的"九字魔咒"，对上说明变体参数没配错；

② 查表法与逐位法各实现一遍，对同一文件跑，两个结果必须逐位一致。两条路线都过，CRC 实现才算过关。

■ 为什么是"左移异或"就是除法？

把数据想成流过寄存器的比特流：每左移一位 = 把下一比特"落"到竖式里；寄存器最高位是 1 说明"够除"，就要减掉除数——模 2 世界里减法就是异或。滚动 8 轮 = 落下一个字节。竖式除法全部滚完剩下的余数，就是寄存器里的值。

LEVEL 3

MD5 第一步：填充、分块、初始化

▶

MD5 的目标：把任意长度的输入压成固定 16 字节指纹。哪怕改 1 个比特，指纹也会面目全非（雪崩效应）。它分四大步：填充 → 分块 → 64 步运算 → 输出。先看前两步。

Step 1：填充（Padding）——把长度凑成"512 的倍数减 64"

以你项目验证用的小例子 "abc"（3 字节 = 24 位）为例：

原始: 'a' 'b' 'c' = 3 字节 第1步: 补一个 0x80（1000 0000） = +1 字节 第2步: 补 0x00 直到总长 ≡ 56 (mod 64) = 补 52 个 0x00 第3步: 末尾补 8 字节 = 原始比特长度(24=0x18) 小端 → 18 00 00 00 00 00 00 00 ─────────────────────────────────────────────── 结果: 3 + 1 + 52 + 8 = 64 字节 = 512 位，正好一块
⚠ 坑：长度是小端！

最后 8 字节长度字段按小端（低位字节在前）写——0x18 放第一个字节。这和网络协议常见的大端习惯相反，实现时写反了指纹必然不对，而且没有任何报错。

■ 为什么留 64 字节？

512 位一块里留出 64 位专门放长度——让"消息内容"和"消息长度"都参与运算，防止不同长度的消息填充后长得一模一样。规则精确到 length ≡ 448 (mod 512)。

Step 2：分块——512 位一块，切成 16 个 32 位字

64 字节一块，按小端切成 16 个 32 位整数 M[0]…M[15]，后面 64 步运算就是反复取用这 16 个字。

Step 3：初始化——四个魔数链值

A = 0x67452301 B = 0xEFCDAB89 C = 0x98BADCFE D = 0x10325476

这四个值看起来乱，小端逐字节读出来是 0123 4567 89AB CDEF FEDC BA98 7654 3210——初代实现者留的彩蛋。它们叫链值（chaining variables），是整个 MD5 唯一的状态载体。

■ 中间结果

无论输入多长，经过填充分块后都变成 N 个 512 位块，并带着 4 个初始链值 A/B/C/D 准备进入主运算。你的 MD5_CTX 结构体里存的就是这 4 个链值 + 已缓冲的未满块。

LEVEL 4

MD5 第二步：64 步主运算 + 链值累积

▶

Step 4：每块 64 步——同一个公式换四种调料

每一块做 64 步，全部长一个模样，只有三样东西在换：非线性函数 F、消息字 M[k]、常量 T[i]：

a ← b + ( ( a + F(b,c,d) + M[k] + T[i] ) <<< s )
轮次步数函数 F性格
第1轮 (0-15)16(b&c)|(~b&d)若 b 真 → 取 c，否则取 d（选择）
第2轮 (16-31)16(b&d)|(c&~d)多数表决
第3轮 (32-47)16b^c^d奇偶（异或三连）
第4轮 (48-63)16c^(b|~d)伪随机放大
  • M[k]：当前块的 16 个消息字按各轮的打乱顺序取用（第 1 轮顺序取，后面轮次按固定乱序表取——让每个消息字影响多处）；
  • T[i]：64 个常量，T[i] = floor(2³² × |sin(i+1)|)——就是正弦表，第一个是 0xD76AA478，作用是打散规律；
  • <<< s：循环左移，每轮的移位数也是固定表（7,12,17,22 / 5,9,14,20 / 4,11,16,23 / 6,10,15,21）。
  • a,b,c,d：四个链值每步循环换位轮转，一步只改一个。

Step 4.5：块的收尾——链值累加

A = A0 + A' ; B = B0 + B' ; C = C0 + C' ; D = D0 + D' （初始链值 + 本块64步的输出，模2³²加法）

Step 5：块与块之间——链值接力

这就是"累积指纹"的核心：上一块输出的链值，是下一块的初始链值。块与块之间没有别的通信，全靠这四个 32 位数接力：

输出：16 字节指纹

最后一块消化完，把 A、B、C、D 四个链值按小端级联成 16 字节，就是 MD5 值。

■ 验证卡：标准答案复核

你实现的 MD5 对 "abc" 算出来的指纹必须是：

90015098 3cd24fb0 d6963f7d 28e17f72

这是 RFC 1327 时代的标准测试向量（严格说出自 RFC 1321 附录），全网通用。对上了 = 填充、小端、64 步、级联全对；错一位 = 回去查填充或端序。你的 md5.c 还可以和上位机工具互验：两端对同一个 .bin 算指纹，必须逐字节一致。

■ 映射回你的项目：三段式 API

MD5Init() = 装入四个魔数链值；MD5Update() = 喂一块（不满 64 字节先攒着）；MD5Final() = 自动补齐最后一块（含填充+长度）并输出 16 字节。Boot_Decrypt_Copy 边解密边喂 Update，1KB 缓冲满一次喂一次，最后 Final 出的 digest 和密文包尾部预留的 16 字节 memcmp——过了，固件才算完整。

■ 为什么两个都要？——层次不同，职责不同

CRC 管的是"路上有没有颠坏"：粒度细到每帧，坏了立刻重传，代价最小。MD5 管的是"最终交货对不对"：粗到整个文件，最后总验收一次。如果只有 CRC，帧内误码全被拦住，但"上位机打包时文件就错了"或"Flash 存储期间坏块"这类非传输层问题没人管；如果只有 MD5，坏一帧就得整包重来。两层嵌套，各管一段，漏检概率相乘后才算总风险。

你项目的三层校验全景

第1层 Ymodem帧级 CRC16-CCITT → 坏帧NAK重传 （传输层） 第2层 结构级 包长互验 → 16B头(固件大小) ↔ 密文包总长（防截断） 第3层 文件级 MD5整包指纹 → 边解密边累积,尾部比对（验收层） ↳ 三层全过,密文才敢解密、固件才敢搬运、App才敢转正
■ 中间结果

回到和 AES 的合影：AES 管"看不懂"，CRC 管"路上没坏"，MD5 管"交货对版"——加密、帧检、验收，三件套各司其职，谁也不能替谁。

BOSS战警告

五个最容易被钓死的坑

▶
坑1：MD5 长度字段按大端写。 正解：64 位长度是小端，低位字节在前——写反不报错，指纹全错。
坑2：把 CRC 初值背成 0xFFFF。 正解：CRC16/XMODEM 初值是 0x0000；0xFFFF 是另一个变体（CRC-CCITT FALSE）。品种三件套（初值/反射/异或）必须两端一致，用"123456789"→0x31C3 验品种。
坑3：以为 CRC 算整帧含帧头。 正解：Ymodem 的 CRC 只覆盖数据区（128/1024 字节），帧头帧号不在其内；帧号的完整性由"seq+反码=255"单独守护。
坑4：把 MD5 的链值和 AES 的 IV 搞混。 正解：长得像，职责不同——IV 是"本组密文的异或搭档"，链值是"上一块消息的消化产物"。IV 由密文前移，链值由压缩函数更新。
坑5：对密文算 MD5。 正解：包尾指纹是上位机对"明文"算的，Boot 必须边解密边对解出来的明文喂 Update——对密文算等于给错了考卷，永远比对失败。
